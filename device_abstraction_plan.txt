Reasoning and Goals
- We want to evolve TinyODOM-EX from “Arduino-only tooling” into a multi-vendor tool that can target different boards (Arduino, STM, etc.) without rewriting the NAS/HIL loop.
- A dict of device specs is easy to extend, but it does not solve vendor-specific behavior: different CLIs, upload steps, log formats, and board quirks (e.g., Portenta core selection).
- The right abstraction is a stable device interface (contract) that the NAS/HIL orchestration calls. Each board implements the contract and owns its toolchain specifics.
- This keeps the core pipeline stable while allowing vendor-specific implementations to vary independently.

File Responsibilities (What goes where)

1) src/tinyodom/devices.py
- Purpose: Defines the contract and shared types. Minimal logic.
- Contents:
  - DeviceSpec dataclass
  - DeviceMetrics dataclass
  - CompileResult / UploadResult / MeasureResult dataclasses
  - DeviceInterface ABC (compile / upload / measure / evaluate)
  - Legacy DEVICE_SPECS catalog (temporary, with FIXME for posterity)
  - ArduinoDevice bridge (temporary, with FIXME for removal)

2) src/tinyodom/microcontrollers/arduino_base.py
- Purpose: Shared Arduino CLI logic and log parsing.
- Contents:
  - Arduino CLI resolution (bin + config)
  - Compile helpers (compile_sketch, parse memory, overflow classification)
  - Upload helpers (upload_sketch)
  - Serial helpers (collect latency, parse power)
  - Sketch constant patching
  - Retry hint parser for arena sizing

3) src/tinyodom/microcontrollers/arduino_ble33.py
- Purpose: Arduino Nano 33 BLE Sense implementation.
- Contents:
  - DeviceSpec for Nano 33 BLE Sense
  - Device subclass with Nano-specific defaults
  - Uses arduino_base helpers

4) src/tinyodom/microcontrollers/arduino_portenta_h7.py
- Purpose: Arduino Portenta H7 implementation.
- Contents:
  - DeviceSpec for Portenta H7
  - Core-selection handling
  - Overrides Arduino base logic where needed

5) src/tinyodom/microcontrollers/stm32_nucleo_n657x0.py
- Purpose: STM NUCLEO-N657X0-Q implementation.
- Contents:
  - DeviceSpec for N657X0
  - STM toolchain hooks (CubeProgrammer/OpenOCD/CMake)
  - Custom compile/upload parsing

6) src/tinyodom/hardware.py
- Purpose: Orchestrator (HIL controller) and conversion helpers.
- Contents:
  - Keeps Keras/TFLite/C conversion helpers
  - Uses DeviceInterface.compile/upload/measure
  - No Arduino toolchain code (Phase 2+)

7) src/tinyodom/model.py
- Purpose: NAS/training orchestration.
- Contents:
  - Builds models, scores trials, calls HIL controller
  - Remains unchanged except for device selection later

8) src/tinyodom/data.py
- Purpose: Dataset loading and preprocessing.
- Contents:
  - Stays unchanged

Phased Migration Plan (Expanded)

Phase 1 (Low-risk scaffolding) — DONE
- Added DeviceSpec, DeviceMetrics, DeviceInterface to devices.py with NumPy-style docstrings.
- Moved legacy DEVICE_SPECS to devices.py with a FIXME note (posterity during migration).
- Added ArduinoDevice bridge class with a FIXME note.
- Updated hardware.py to import DEVICE_SPECS from devices.py (no behavior change).

Phase 1.B (Next: update call sites to use devices abstractions)
- Add a minimal device selection path in hil_server.py and nas_model_client.py:
  - Instantiate ArduinoDevice via config.device.name.
  - Call device.evaluate(...) instead of direct HIL_controller where feasible.
- Keep the existing HIL_controller path available for fallback.
- Update tests to allow either path (or add a small unit test that device.evaluate returns the same tuple).
- Ensure metrics/CSV logging fields remain unchanged.

Phase 2 (Mechanical refactor) — DONE
- Moved Arduino-specific code out of hardware.py into microcontrollers/arduino_base.py:
  - CLI invocation (compile/upload) logic.
  - Serial log parsing for latency/energy.
  - Sketch constant patching helpers.
- Updated ArduinoDevice to use the moved helpers.
- Updated HIL_spec/HIL_controller to use device.compile/upload/measure.
- Updated tests to patch/import moved helpers from microcontrollers/arduino_base.py.

Phase 3 (Add vendor-specific devices)
- Implement STM32 device class in microcontrollers/stm32_nucleo_n657x0.py.
  - Decide the toolchain (CubeProgrammer/OpenOCD/CMake) and create compile/upload hooks.
  - Map toolchain logs into the standard DeviceMetrics.
- Implement Portenta H7 class with core selection handling.
  - Add core-selection parameter into compile/upload step.
- Extend the registry/selection logic to include new devices.
- Add at least one integration test per device class (even if it’s a mocked toolchain run).

Phase 4 (Clean-up and hardening)
- Remove remaining Arduino-specific code from hardware.py.
  - hardware.py should be orchestration + conversion only.
- Remove legacy DEVICE_SPECS and ArduinoDevice bridge once per-device classes are wired.
- Standardize error codes and metrics across all devices.
- Expand tests to cover registry resolution and error cases.
- Document device onboarding steps in README (or a dedicated docs file).

Notes / Design Constraints
- Device classes should own all vendor-specific logic (CLI flags, parsing, serial quirks).
- hardware.py should remain the stable orchestrator and not become device-specific again.
- Keep the NAS loop and entry points stable (nas_model_client.py, hil_server.py).
- Make sure the device interface includes all required parameters (serial_port, window_size, channels, arena sizes).
